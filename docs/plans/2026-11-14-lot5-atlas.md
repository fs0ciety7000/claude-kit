# Lot 5 — Hub de docs `atlas`

Plan v2 : `docs/plans/2026-11-12-harness-v2.md`, lot 5. Rythme du 13/11 : revue de sécurité seulement là où il y a
secrets, accès ou exposition (5a) ; fusion dès que la CI est verte ; une liste d'actions en fin de lot.

Le dépôt privé `atlas` existe déjà mais ne contient qu'une ancienne copie de gabarit jamais utilisée : il est
**remplacé** (l'ancien contenu reste dans l'historique Git et la sauvegarde Forgejo). Contenu écrit de zéro : rien
n'est repris de l'ancien coffre de notes ni du site de doc de l'infra.

## Sous-lots

- [x] **5a — Site** (agent `frontend-dev`, revue `security-reviewer`)
  - Starlight (dernière version stable), site statique, image nginx non root, aucune ressource externe, recherche
    locale (Pagefind) ; CI Forgejo (gabarit `astro`).
  - **Ni build local ni CSP à régénérer à la main** (demande du propriétaire, 14/11) : le build et le calcul de la
    CSP par empreintes se font dans l'étape de build du Dockerfile (Coolify construit à la fusion) ; rien de généré
    n'est commité. Une modification de contenu = un fichier Markdown et une PR ; la CI vérifie, Claude ne construit
    pas le site en local.
  - Mis en ligne par `/ship` en `expose: access`, domaine `atlas.<zone principale>` (le premier vrai passage de
    `/ship`).
- [x] **5b — Modèle de contenu et contenu de départ** (agent `copywriter`, lecture seule ailleurs)
  - Sections : Projets (une page par projet), Services (catalogue : rôle, où il tourne, comment l'utiliser,
    réutilisable ou non), Infra (vue d'ensemble par rôles, procédures), Piles (notes par stack du kit), Leçons (une
    idée par page, datée, liée).
  - Frontmatter validé par le schéma Starlight (`type`, `updated`, `tags`, `status`) ; contrôle en CI : liens
    internes, aucune IP, aucun e-mail, aucun secret.
  - Contenu de départ écrit à partir des dépôts (infra, kit, pont) : infra et services en rôles, leçons tirées des
    pièges déjà rencontrés.
- [x] **5c — Pages projet générées** (agent `devops`)
  - `kit atlas sync` : depuis un projet, écrit `projets/<nom>.md` à partir de `project.yaml`, `plan.md` et
    `docs/memory/state.md` (résumé, taille, pile, exposition, URL, état, prochaines étapes) et ouvre une PR sur
    `atlas`. Appelé par `/ship`, `/retire` et `/handoff`. Aucun jeton côté CI : c'est la session du projet qui écrit.
- [x] **5d — Skill `atlas` et retrait d'engram** (agent `devops`)
  - Skill `atlas` : chercher (projet, service ou leçon réutilisable) dans un clone local à jour, écrire seulement à
    la demande, par PR.
  - Le skill `engram` et ses agents quittent le kit ; le dépôt `engram` et son application sont listés pour le
    propriétaire (archivage, arrêt) : rien n'est supprimé par Claude.

## Fait quand

`atlas` répond en HTTPS derrière Access, avec le contenu de départ ; `kit atlas sync` crée la page d'un projet par PR ;
le skill `atlas` retrouve un service ou une leçon ; tests et CI verts.

## État (14/11)

5a à 5d fusionnés (site, contenu de départ, thème validé, `kit atlas sync`, skill `atlas`, engram retiré du kit).
