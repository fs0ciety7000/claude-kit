# Lot 4 — Livrer (ex-lots 4 et 6 du plan v2)

Plan v2 : `docs/plans/2026-11-12-harness-v2.md`. Rythme révisé le 13/11 : revue de sécurité seulement sur ce qui
touche secrets, accès ou exposition (ici : 4a et 4c) ; fusion par Claude dès que la CI est verte ; une seule liste
d'actions du propriétaire en fin de lot.

## Principe

Le dépôt d'infra reste la source de vérité du DNS, d'Access et des sondes : le kit y **ouvre une PR**, le
propriétaire lance `tofu apply`. Coolify et le pont sont pilotés par `kit api` (écritures autorisées, jamais DELETE).
La première mise en prod d'un projet reste une validation du propriétaire.

## Sous-lots

- [x] **4a — `project.yaml` et `/ship`** (agent `devops`, revue `security-reviewer`)
  - `project.yaml` : `expose: none|tailnet|access|public`, `domain`, `server`, `coolify_uuid`, `health_path`,
    `volumes` (oui/non).
  - `kit ship plan` : ce qui sera créé ou modifié, sans rien écrire.
  - `kit ship infra` : branche et PR dans le dépôt d'infra (DNS vers le tunnel, application Access si `access`,
    sonde Gatus si `public`, sauvegarde du volume si `volumes`).
  - `kit ship app` : application Coolify depuis le dépôt GitHub (source App GitHub, auto-déploiement coupé,
    domaine, contrôle des noms de variables contre l'exemple du projet, sans valeurs), `.fs0/bridge.yaml`
    (`deploy:` sur `main`), entrée `owner/repo=uuid` ajoutée à `DEPLOY_ALLOW` du pont.
  - `/ship` : enchaîne plan, validation (première fois seulement), infra, app, attend le déploiement et le HTTPS,
    écrit `coolify_uuid` et l'URL dans `project.yaml`.
- [x] **4b — `/retire`** (agent `devops`)
  - Arrête l'application (`stop`), retire l'entrée de `DEPLOY_ALLOW`, coupe `deploy:`, PR d'infra qui retire DNS,
    Access et sonde. Suppression de l'application Coolify et archivage du dépôt : listés pour le propriétaire.
- [x] **4c — Prévisualisations par PR** (agent `devops`, revue `security-reviewer`)
  - Web en taille M ou L : prévisualisations Coolify des PR, toujours derrière Access, sous un sous-domaine
    joker dédié (une PR d'infra unique : DNS joker et application Access).
  - `project.yaml` : `previews: true|false` ; `/ship` les active, `/retire` les coupe.
- [x] **4d — Lanceur `/new`** (agent `devops`)
  - `kit new <nom> --stack <pile> [--size S|M|L]` : dépôt GitHub privé (`kit repo create`), gabarit, CI
    (`kit project ci`), permissions, `project.yaml`, équipe recommandée, plan ; même parcours en local
    (`claude remote-control` pour suivre) et en session cloud.
  - `/new-project` délègue à `kit new` (moins de mots, mêmes deux validations).
  - Environnement cloud « fs0 » : à proposer au propriétaire (hôtes nécessaires seulement), pas créé d'office.

## Fait quand

Un projet de test (site Astro) passe de `kit new` à une URL HTTPS par `/ship`, reçoit une prévisualisation sur une
PR, puis est retiré par `/retire` ; tests du kit verts.

## État (13/11)

4a à 4d fusionnés (PR #51 à #54). Reste la recette de bout en bout sur le poste du propriétaire (`ship.conf`, `tofu apply`,
première mise en prod validée).
